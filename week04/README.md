# 4주차 실습 — 보이는 환경에 자원 한도를 더하다

[전체 주차 목록](https://github.com/choong-syu/cloud-virtualization) · [3주차 실습](https://github.com/choong-syu/cloud-virtualization/blob/main/week03/README.md)

3주차에는 프로세스가 보는 `/`, hostname, PID를 나누었습니다. 이번에는 그 실행 환경 안의 프로그램이 **CPU와 메모리를 얼마나 사용할 수 있는지** 직접 정하고 결과를 관찰합니다.

같은 프로그램을 계속 실행한 채 한도만 바꾸어 봅니다. CPU에서는 실행 시간과 계산량을, 메모리에서는 현재 사용량과 허용 상한의 차이를 확인합니다.

- **터미널 A:** 실습을 진행하는 SSH 창. 명령 18 이후에는 내부 BusyBox `sh`입니다.
- **터미널 B:** 같은 VM에 별도로 접속한 호스트 관찰용 SSH 창입니다.
- 명령 제목에 적힌 실행 위치를 먼저 확인하고, 명령 블록을 하나씩 실행합니다.
- 예상 결과는 입력하지 않습니다. PID와 사용량은 자신의 출력값으로 비교합니다.

**진행 요령:** CPU는 명령 37~49, 메모리는 명령 53~61을 먼저 읽고 실행합니다. 프로그램을 켠 동안에는 측정에 집중하고, Ctrl+C로 멈춘 뒤 표를 채우며 해석합니다. 여러 단계의 명령을 한꺼번에 붙여 넣지 않습니다. CPU 측정에서 “블록 전체 실행”이라고 표시한 부분만 묶어서 실행합니다.

화면의 `student…@vm…:~$`는 호스트의 일반 사용자 셸, `/ #`는 이번 실습의 내부 BusyBox 셸 예시입니다. 이 프롬프트 자체는 입력하지 않습니다. A에서 프로그램의 숫자가 계속 나오거나 자료를 보관하는 중에는 새 셸 명령을 입력하지 않고, B로 이동해 관찰합니다.

## 처음 한 번: 실습 환경 준비

각 명령 제목에는 **01번부터 이어지는 번호**, **실행할 터미널**, **확인할 내용**을 표시합니다. 준비 과정부터 순서대로 번호를 매겼습니다. `(터미널 A·B 각각)`이면 두 창에서 각각 실행하고, `(터미널 A)`이면 A에서만 실행합니다. 번호와 제목은 입력하지 않고 코드 블록을 복사합니다.

`\`로 이어지는 여러 줄과 `|`로 연결한 파이프는 각각 하나의 명령으로 셉니다. 오류 해결과 선택 실습은 **해당 상황에서만 실행**합니다. CPU 측정의 명령 39~41과 45~47은 한 블록으로 이어 실행하며, 블록 안의 `#`로 시작하는 번호·설명은 그대로 복사해도 되는 주석입니다.

**3주차에서 만든 파일과 rootfs가 없는 상태에서 시작합니다.** 아래 준비 과정을 터미널 A의 일반 사용자 호스트 Bash에서 실행합니다. 학생별 Ubuntu/Debian Linux VM, 인터넷 연결과 `sudo` 권한이 필요하며, 제공 실행 파일은 x86-64용입니다. VM은 systemd와 cgroup v2를 사용해야 합니다.

### 준비 순서

**가. 파일을 내려받을 도구를 준비합니다.**

패키지 목록을 갱신합니다.

#### 01. (터미널 A · 호스트) **패키지 목록 갱신**

```bash
sudo apt-get update
```

`wget`을 설치합니다.

#### 02. (터미널 A · 호스트) **다운로드 도구 설치**

```bash
sudo apt-get install -y --no-upgrade wget
```

`sudo`가 암호를 물으면 실습 계정의 암호를 입력합니다. 입력 중 글자나 별표가 보이지 않는 것은 정상입니다.

**나. 홈 디렉터리에서 4주차 준비 스크립트를 내려받습니다.**

#### 03. (터미널 A · 호스트) **홈 디렉터리로 이동**

```bash
cd "$HOME"
```

학교 VM에서 사용하는 GitHub 다운로드 주소입니다. 아래 여러 줄은 하나의 명령입니다.

#### 04. (터미널 A · 호스트) **4주차 준비 스크립트 내려받기**

```bash
wget --timeout=15 --tries=2 \
  --header='Accept: application/vnd.github.raw+json' \
  -O week04-setup.sh \
  'https://api.github.com/repos/choong-syu/cloud-virtualization/contents/week04/scripts/setup.sh?ref=main'
```

다운로드가 성공하면 다음 실행 단계로 이동합니다. 오류가 나면 실행하지 말고 다운로드 오류부터 확인합니다. [준비 스크립트 내용 보기](scripts/setup.sh)

**다. 준비 스크립트를 실행합니다.**

#### 05. (터미널 A · 호스트) **rootfs와 부하 프로그램 준비**

```bash
bash week04-setup.sh
```

앞에 `sudo`를 붙이지 않습니다. 필요한 설치 작업에서만 스크립트가 관리자 권한을 사용합니다. 완료 메시지가 나올 때까지 기다립니다.

준비가 끝나면 다음 파일이 만들어집니다.

```text
사용자 홈/
└── cloud-virtualization/
    ├── assets/
    │   └── busybox-rootfs/             ← 3주차 방식으로 만든 rootfs
    │       ├── bin/                   ← BusyBox 명령과 부하 프로그램
    │       ├── etc/                   ← 실습용 설정 파일
    │       └── proc/                  ← 아직 비어 있는 폴더
    └── week04/
        └── scripts/
            ├── restore-week03.sh      ← 지난주 실행 환경을 여는 스크립트
            ├── resource-workload-linux-x86_64
            └── resource-workload.c    ← 부하 프로그램의 소스
```

rootfs는 프로세스에게 `/`로 보여 줄 파일 트리입니다. 준비 과정에서 정적 BusyBox와 기본 명령, 설정 파일을 처음부터 만듭니다. `tmp`, `dev`, `home`, `mnt` 폴더도 함께 준비됩니다.

`resource-workload`는 계산을 반복하거나 메모리에 자료를 보관하는 작은 프로그램입니다. 자원 한도는 이후 학생이 직접 설정합니다. 준비 스크립트는 파일을 갖추는 단계이며, **namespace·procfs·chroot 실행 환경은 본편 명령 18에서 자원 그룹 안에 만듭니다.**

#### 11. (터미널 A · 호스트) **rootfs의 준비된 폴더 확인**

```bash

```

### B에서 기능과 기록 폴더 확인

먼저 이번에 사용할 이름을 구분합니다.

| 이름 | 이번 실습에서의 뜻 |
| --- | --- |

## 1. 같은 그룹 안에서 지난 환경 복원

### 자원 그룹을 직접 만들고 이전 환경 복원

이제 준비한 파일 재료로 실제 실행 환경을 시작합니다. **먼저 이번 실습의 cgroup을 만들고, 그 안에서 지난주 구성을 시작**합니다. 이렇게 하면 내부 셸과 그 셸이 실행하는 부하 프로그램이 처음부터 같은 실습 그룹에 속합니다. 따로 켜 둔 지난주 셸의 소속을 나중에 옮기는 과정은 필요하지 않습니다.

**예상:** 이 명령으로 시작한 프로세스와 이후 자식 프로세스는 같은 실습 cgroup에 속합니다. 처음 정책은 CPU 1개 상당, 메모리 128MiB, swap 사용 상한 0입니다. MiB는 메모리 크기 단위이며 1MiB는 1,048,576바이트입니다.

swap은 RAM의 일부 내용을 옮겨 둘 수 있는 디스크 공간입니다. 이번에는 이 그룹의 swap 사용을 막아 RAM 사용량과 상한을 비교합니다. `-p`는 뒤에 적은 속성값을 설정한다는 뜻이며, `CPUQuota`는 CPU 시간 상한, `MemoryMax`는 메모리 상한, `MemorySwapMax`는 swap 상한입니다. 모두 아래 명령의 옵션으로 적으며, 별도 설정 파일을 편집하지 않습니다.

아래 전체는 줄만 나눈 **한 명령**입니다. `\`는 다음 줄로 이어짐을 뜻합니다.

#### 18. (터미널 A · 호스트 → 내부 BusyBox sh) **자원 그룹을 만들고 지난 환경 복원**

```bash
sudo systemd-run --scope --unit="$UNIT" \
  -p CPUQuota=100% \
  -p MemoryMax=128M \
  -p MemorySwapMax=0 \
  -p TimeoutStopSec=5s \
  /bin/bash "$WORK/scripts/restore-week03.sh" enter "$ROOTFS"
```

앞부분 `systemd-run --scope`와 `-p`들은 **학생이 직접 그룹과 정책을 정하는 부분**입니다. 뒤의 스크립트 `enter`는 지난주에 배운 다음 순서를 출력하며 복원합니다.

1. `unshare`로 UTS·PID·Mount namespace를 만듭니다.
2. 내부 hostname을 `cv-resource-lab`으로 정합니다.
3. 새 PID 관점의 procfs를 rootfs 아래에 마운트합니다.
4. `exec chroot`로 PID 1 Bash를 BusyBox `sh`로 바꿉니다.

스크립트는 cgroup 소속을 옮기거나 자원 정책을 설정하지 않습니다. `TimeoutStopSec=5s`는 **중지를 요청한 뒤 기다릴 시간**이며 실습을 5초 만에 종료하는 설정이 아닙니다.

**확인:** 네 과정이 나오고 A가 내부 셸로 들어갑니다. 화면에 나오는 기존 안내 “README 명령 02”는 이 문서의 **명령 19~22 — 지난주 관점 확인**을 뜻합니다. B는 호스트에 그대로 둡니다. `STOP`이나 오류가 있으면 다음 명령으로 가지 않습니다.

### 지난주 관점 확인

#### 19. (터미널 A · 내부 BusyBox sh) **내부 hostname 확인**

```sh
hostname
```

#### 20. (터미널 A · 내부 BusyBox sh) **현재 셸의 내부 PID 확인**

```sh
echo "$$"
```

#### 21. (터미널 A · 내부 BusyBox sh) **PID 1의 프로그램 이름 확인**

```sh
cat /proc/1/comm
```

#### 22. (터미널 A · 내부 BusyBox sh) **rootfs의 hostname 파일 읽기**

```sh
cat /etc/hostname
```

**예상 결과:** 차례로 `cv-resource-lab`, `1`, `sh`, `busybox-rootfs`입니다. `$$`는 현재 셸 PID입니다. 현재 UTS hostname과 파일 `/etc/hostname`의 내용은 다른 대상이므로 이름이 달라도 정상입니다.

**확인:** 준비한 rootfs로 3주차에서 배운 관점이 만들어졌습니다. 이제부터는 이 실행 환경을 유지하면서 자원 정책과 결과를 연결합니다. 다음 명령 23~36에서는 “이 안의 프로세스가 밖에서 보는 어느 그룹에 속하는가?”를 확인합니다.

### 프로세스에서 cgroup 소속 찾기

#### 23. (터미널 A · 내부 BusyBox sh) **내부 PID 1의 cgroup 소속 확인**

**출력 예 — 입력하지 않습니다:**


`0::` 뒤가 실제 cgroup 경로입니다. 마지막 이름이 실습 시작 전에 `UNIT`에 저장한 이름인지 봅니다. 원래 프로세스에 cgroup 소속이 없었던 것이 아니라, 이번에 **우리 실습 그룹 안에서** 실행한 것입니다.

### systemd에서 같은 그룹 찾기

#### 24. (터미널 B · 호스트) **실행 상태와 cgroup 경로 확인**

```bash

```

**확인:** `ActiveState=active`이며, `ControlGroup=` 뒤 경로가 A의 `0::` 뒤 경로와 같습니다. 안의 프로세스와 밖에서 관리할 대상이 연결되었습니다.

### 읽을 경로 저장

`--value`는 항목 이름을 빼고 값만 출력합니다.

**먼저 확인:** 값이 비어 있지 않고 `/`로 시작하며 마지막 이름이 `"$UNIT"`과 같습니다. 빈 값이나 `/` 하나뿐이면 멈춥니다.

**관찰:** 그룹의 프로세스들이 보입니다. B의 숫자는 호스트 PID이므로 A의 내부 PID 1과 달라도 정상입니다. `--no-pager`는 별도의 페이지 화면 없이 바로 출력하게 합니다.

## 2. 같은 프로그램의 CPU 시간 상한 변경

### 같은 계산 프로그램 시작

**명령 38~49를 먼저 읽고 B의 관찰 위치까지 준비한 뒤** 시작합니다. 프로그램은 최대 180초 후 자동 종료하므로 측정을 먼저 마치고 멈춘 다음 토의합니다. 자동 종료되면 [재시작 안내](#180초가-먼저-끝남)로 이동합니다.

#### 37. (터미널 A · 내부 BusyBox sh) **CPU 계산 프로그램 시작**

```sh
/bin/resource-workload cpu
```

`elapsed_s,pid,iterations_per_second`는 경과 시간, 내부 PID, 실제 경과 시간당 계산 반복 횟수입니다. PID를 기록합니다. 25%로 바꿀 때도 **이 프로그램을 다시 시작하지 않습니다.**

**출력 읽는 법 — 아래 숫자는 예시이며 입력하지 않습니다:**

```text
elapsed_s,pid,iterations_per_second
4.000,39,400000000
5.000,39,410000000
6.000,39,405000000
```

두 번째 열 `39`가 PID이고, 세 번째 열이 초당 계산 횟수입니다. “계산 횟수 세 개”는 연속된 세 줄의 **세 번째 숫자**를 뜻합니다. A에 조회 명령을 입력하지 않고 화면을 읽습니다. 한도를 바꾼 뒤에는 처음 3초를 지난 출력 세 줄을 읽습니다.

### 100% 구간의 기록 준비

#### 38. (터미널 B · 호스트) **CPU 측정 전 3초 대기**

```bash
sleep 3
```

`cpu.stat`은 누적 통계입니다. `usage_usec`는 사용한 CPU 시간, `nr_periods`는 주기 수, `nr_throttled`는 제한된 주기 수, `throttled_usec`는 제한으로 지연된 시간 통계입니다. `usec`는 마이크로초입니다.

`|`는 앞의 출력을 뒤로 넘기는 파이프이고, `tee`는 화면과 파일에 같은 내용을 기록합니다. 한도를 바꾸는 명령이 아닙니다.

다음 단계에서는 시작값을 저장하고, 5초 기다린 뒤 끝값을 저장합니다. 숫자가 처음부터 0이 아니어도 정상입니다. 같은 조건의 끝값에서 시작값을 뺍니다.

### 100% 구간을 약 5초 측정

**아래 세 명령은 블록 전체를 한 번에 붙여 넣어 실행합니다.** `cat`으로 시작값 기록 → `sleep 5`로 5초 대기 → `cat`으로 끝값 기록 순서입니다. 중간에 설명을 읽거나 다음 명령을 찾느라 측정 시간이 길어지지 않게 합니다.

#### 39~41. (터미널 B · 호스트) **CPU 100% 구간을 약 5초 동안 연속 기록**

```bash
# 39. CPU 100% 구간의 시작값 기록
cat "$CG/cpu.stat" | tee "$OBS/cpu-100-before.txt"
# 40. CPU 100% 구간에서 5초 대기
sleep 5
# 41. CPU 100% 구간의 끝값 기록
cat "$CG/cpu.stat" | tee "$OBS/cpu-100-after.txt"
```

A의 계산 횟수 세 개도 기록합니다. 파일을 읽고 기록하는 짧은 시간이 포함되므로 정확히 5.000초는 아닙니다. 두 조건 모두 같은 방식으로 약 5초 동안 비교하며, 증가량 자체를 정확한 초당 값이라고 부르지 않습니다.

### CPU 시간 상한만 25%로 변경

**예상:** PID는 같고, CPU 실행 시간과 계산량은 줄어들 수 있습니다. `set-property`는 속성 변경, `--runtime`은 재부팅 뒤의 영구 설정으로 저장하지 않는 현재 실행 환경의 변경입니다.

#### 42. (터미널 B · 호스트) **CPU 시간 상한을 25%로 변경**

```bash
sudo systemctl set-property --runtime "$UNIT" CPUQuota=25%
```

#### 43. (터미널 B · 호스트) **변경한 CPU 시간 상한 확인**

```bash
cat "$CG/cpu.max"
```

**출력 예:**

```text
25000 100000
```

100ms의 주기에 합계 최대 25ms의 CPU 시간을 허용합니다. VM 전체의 CPU 속도를 변경한 것이 아닙니다.

### 같은 PID의 25% 구간 기록

변경 직후는 두 조건이 섞일 수 있으므로 기다린 뒤 시작합니다.

#### 44. (터미널 B · 호스트) **CPU 상한 변경 후 3초 대기**

```bash
sleep 3
```

**아래 세 명령도 블록 전체를 한 번에 실행합니다.** 100% 구간과 같은 방식입니다.

#### 45~47. (터미널 B · 호스트) **CPU 25% 구간을 약 5초 동안 연속 기록**

```bash
# 45. CPU 25% 구간의 시작값 기록
cat "$CG/cpu.stat" | tee "$OBS/cpu-25-before.txt"
# 46. CPU 25% 구간에서 5초 대기
sleep 5
# 47. CPU 25% 구간의 끝값 기록
cat "$CG/cpu.stat" | tee "$OBS/cpu-25-after.txt"
```

A에서 같은 PID인지 확인하고 안정된 계산 횟수 세 개를 기록합니다. 100%의 시작·끝, 25%의 시작·끝을 **각각 한 쌍**으로 비교합니다.

### 부하를 멈추고 CPU 상한 복원

**A에서 Ctrl+C**를 눌러 BusyBox 셸로 돌아옵니다. 아직 `exit`하지 않습니다. 이어서 **B에서** 실행합니다.

#### 48. (터미널 B · 호스트) **CPU 시간 상한을 100%로 복원**

```bash
sudo systemctl set-property --runtime "$UNIT" CPUQuota=100%
```

#### 49. (터미널 B · 호스트) **복원한 CPU 시간 상한 확인**

```bash
cat "$CG/cpu.max"
```

비율이 다시 1인지 봅니다. 다음 메모리 실험에 CPU 25%의 영향을 남기지 않기 위한 복원입니다.

### 설정·실행 시간·지연 설명

부하를 멈춘 뒤 B에서 기록 파일을 다시 읽을 수 있습니다.

#### 50. (터미널 B · 호스트) **CPU 100%의 시작값과 끝값 다시 읽기**

```bash
cat "$OBS/cpu-100-before.txt" "$OBS/cpu-100-after.txt"
```

시작 파일의 내용이 먼저, 끝 파일의 내용이 그다음 나옵니다.

#### 51. (터미널 B · 호스트) **CPU 25%의 시작값과 끝값 다시 읽기**

```bash
cat "$OBS/cpu-25-before.txt" "$OBS/cpu-25-after.txt"
```

예를 들어 한 조건의 `usage_usec`가 시작 `2000000`, 끝 `7000000`이면 증가량은 `5000000µs`, 즉 약 5 CPU초입니다. **100%의 시작·끝끼리, 25%의 시작·끝끼리** 뺍니다. 두 조건의 누적 끝값을 서로 빼지 않습니다. 자신의 관찰 노트에 채웁니다.

| 항목 | CPU 100% | CPU 25% |
| --- | --- | --- |
| 같은 내부 PID인가? |  |  |
| quota ÷ period |  |  |
| `usage_usec` 끝 − 시작 |  |  |
| `nr_throttled` 끝 − 시작 |  |  |
| `throttled_usec` 끝 − 시작 |  |  |
| A의 안정된 계산 횟수 세 개 |  |  |

**기존 vm45 실측 예:** 약 5초 구간의 CPU 사용 시간은 `5,011,599µs`(약 5.01 CPU초)에서 `1,250,658µs`(약 1.25 CPU초)로 줄었고, 제한된 주기의 증가량은 0에서 50으로 늘었습니다. 자신의 숫자를 이 값에 맞추지 않습니다.

주된 근거는 **실제 상한과 CPU 실행 시간·지연 기록**입니다. A의 처리량 감소는 보조 자료입니다. CPU 시간 25%가 처리량도 정확히 25%임을 보장하지 않습니다. 기존 실측에서는 처리량이 약 3.1억~4.4억 회/초에서 4,400만~6,500만 회/초로 줄었으며, 그 비율 차이의 원인까지 분리해 검증하지는 않았습니다.

## 3. 메모리의 현재값과 상한 비교

### 자료 생성 전 현재값 기록

#### 52. (터미널 B · 호스트) **자료 생성 전 현재 메모리 기록**

```bash
cat "$CG/memory.current" | tee "$OBS/memory-idle.txt"
```

**관찰:** 0이 아닐 수 있습니다. 내부 셸 등 같은 그룹의 프로세스도 메모리를 사용합니다. `memory.current`는 현재 사용하는 양, `memory.max`는 허용한 상한입니다.

### 자료 48MiB 만들고 보관

명령 54~60을 먼저 읽고 시작합니다.

#### 53. (터미널 A · 내부 BusyBox sh) **48MiB 자료 보관 프로그램 시작**

```sh
/bin/resource-workload memory 48
```

`Press Enter to start`가 나오면 A에서 Enter를 누릅니다. `allocated_mib`가 4씩 늘어 48에 도달하고 `Holding 48 MiB`가 나오는지 봅니다. PID도 기록합니다.

숫자 48은 **자료 크기**이며 그룹의 상한이 아닙니다. 프로그램은 Enter를 최대 60초 기다리고, 그 대기를 포함하여 전체 180초 후 종료합니다. `allocated_mib`는 이 프로그램이 실제 쓰기를 마친 자료량이지 `memory.current`를 읽은 값이 아닙니다.

### 현재값이 새 상한보다 작은지 확인

#### 54. (터미널 B · 호스트) **48MiB 자료 생성 후 현재 메모리 기록**

```bash
cat "$CG/memory.current" | tee "$OBS/memory-48-current.txt"
```

#### 55. (터미널 B · 호스트) **변경 전 메모리 상한 확인**

```bash
cat "$CG/memory.max"
```

**기존 실측 예:** 현재값은 `50995200`바이트(약 48.63MiB), 상한은 `134217728`바이트(128MiB)였습니다. 자료 이외의 그룹 사용량도 포함되므로 정확히 48MiB일 필요는 없습니다.

**다음 조건:** 현재값이 `100663296`바이트(96MiB)보다 작아야 합니다. 그 이상이면 다음 설정을 변경하지 말고 A의 부하를 멈춘 뒤 교수자와 확인합니다.

### 사건 시작값을 기록하고 상한만 낮춤

**예상:** 자료도 전체 사용량도 96MiB보다 작다면 상한만 128→96으로 낮춘다고 반드시 프로그램이 끝나지는 않습니다.

`memory.events`는 누적 사건 기록입니다. `max`는 상한에 걸린 기록, `oom`은 메모리 확보가 어려운 상황, `oom_kill`은 메모리 부족으로 프로세스가 종료된 기록으로 읽습니다. 시작값과 끝값의 차이를 비교합니다.

#### 56. (터미널 B · 호스트) **상한 변경 전 메모리 사건 기록**

```bash
cat "$CG/memory.events" | tee "$OBS/memory-safe-before.txt"
```

#### 57. (터미널 B · 호스트) **메모리 상한을 96MiB로 낮추기**

```bash
sudo systemctl set-property --runtime "$UNIT" MemoryMax=96M
```

### 상한·현재값·사건 다시 읽기

#### 58. (터미널 B · 호스트) **변경한 메모리 상한 확인**

```bash
cat "$CG/memory.max"
```

#### 59. (터미널 B · 호스트) **상한 변경 후 현재 메모리 기록**

```bash
cat "$CG/memory.current" | tee "$OBS/memory-96-current.txt"
```

#### 60. (터미널 B · 호스트) **상한 변경 후 메모리 사건 기록**

```bash
cat "$CG/memory.events" | tee "$OBS/memory-safe-after.txt"
```

**확인:** 상한은 `100663296`바이트입니다. A의 같은 프로그램이 자료를 계속 보관하는지도 봅니다. `Holding 48 MiB` 뒤에는 새 출력이 없어도 정상입니다. 다만 `Stopped…`가 나오거나 `/ #` 프롬프트가 돌아왔다면 프로그램이 끝난 상태입니다. 예전 `Holding` 문구만 보고 계속 실행 중이라고 판단하지 말고 [재시작 안내](#180초가-먼저-끝남)에 따라 다시 측정합니다.

기존 실측에서는 현재값이 `50995200`바이트로 유지되었고 사건 증가는 없었습니다. 상한 96MiB가 현재 사용량을 96MiB로 만드는 것은 아닙니다.

### 자료 사용을 마친 뒤 현재값 읽기

A에서 Ctrl+C로 부하를 멈추고 BusyBox 셸로 돌아옵니다. B에서 읽습니다.

#### 61. (터미널 B · 호스트) **부하 종료 후 현재 메모리 기록**

```bash
cat "$CG/memory.current" | tee "$OBS/memory-stopped.txt"
```

**관찰:** 보관 자료가 해제되어 현재값이 줄어듭니다. 내부 셸과 캐시 등이 남을 수 있어 처음 값과 완전히 같거나 0이어야 하는 것은 아닙니다.

### 메모리 부족은 별도 환경에서 관찰

교수자가 선택한 경우에만 [별도 OOM 실험](#optional-oom)으로 이동합니다. 본편 A의 내부 셸을 그대로 두고 새 호스트 창 C에서 별도 그룹을 만듭니다. 본편의 `UNIT`과 `CG` 값을 바꾸지 않습니다.

선택 실험을 하지 않거나 마쳤다면 명령 68로 이어 갑니다. OOM 개념은 이론에서 배우며 직접 상한 초과를 일으키는 실행은 선택입니다.

### 남은 부하가 없는지 확인

#### 68. (터미널 A · 내부 BusyBox sh) **남은 부하 프로그램 확인**

```sh
ps
```

`resource-workload`가 남아 있으면 먼저 그 부하를 종료합니다. 내부 셸과 확인 명령 등이 보이는 것은 정상입니다.

### procfs 연결 해제

#### 69. (터미널 A · 내부 BusyBox sh) **마운트 해제 전 루트 디렉터리로 이동**

```sh
cd /
```

#### 70. (터미널 A · 내부 BusyBox sh) **내부 procfs 연결 해제**

```sh

```

`cd`는 작업 위치를 바꾸고, `umount`는 마운트 연결을 풉니다. rootfs의 파일을 삭제하는 명령이 아닙니다.

### 내부 셸 종료

#### 71. (터미널 A · 내부 BusyBox sh → 호스트) **내부 셸을 종료하고 호스트로 돌아가기**

```sh
exit
```

호스트 프롬프트가 돌아온 뒤 **따로** 실행합니다.

#### 72. (터미널 A · 호스트) **일반 사용자로 돌아왔는지 확인**

```bash
whoami
```

처음의 일반 사용자여야 합니다. 이번에 rootfs를 사용하던 실행을 끝냈습니다.

### 실행 그룹이 끝났는지 확인

#### 73. (터미널 B · 호스트) **본편 scope의 종료 상태 확인**

```bash
systemctl show "$UNIT" -p LoadState -p ActiveState
```

#### 74. (터미널 B · 호스트) **본편 cgroup 경로가 사라졌는지 확인**

```bash
ls -d "$CG"
```

**확인:** 더는 `active`가 아닙니다. 임시 unit이 회수되어 `not-found`가 나오거나 cgroup 경로가 없어질 수 있습니다. 여기서 `ls`의 파일 없음 메시지는 정상 정리의 결과입니다.

### rootfs 재료 확인

#### 75. (터미널 B · 호스트) **rootfs의 proc 폴더가 비었는지 확인**

```bash
ls -A "$ROOTFS/proc"
```

#### 76. (터미널 B · 호스트) **rootfs 파일이 남아 있는지 확인**

```bash
ls "$ROOTFS"
```

`proc`는 다시 비어 있고 rootfs 재료는 남습니다. rootfs 전체나 `/sys/fs/cgroup` 아래를 직접 삭제하지 않습니다.

### 관찰 노트와 다음 주 연결

#### 77. (터미널 B · 호스트) **저장한 관찰 기록 확인**

```bash
ls "$OBS"
```

CPU와 메모리 기록은 실행 그룹이 사라져도 남습니다. 다음 세 질문에 자신의 값으로 답합니다.

1. 같은 PID의 CPU 시간 상한을 바꾸자 실행 시간과 지연은 어떻게 달라졌는가?
2. 메모리의 현재값과 상한을 어떤 파일로 구별했는가?
3. 자원 한도를 바꾸어도 유지된 관점은 무엇인가?

다음 주에는 같은 rootfs에 별도의 Network namespace를 만들고 연결을 더합니다. 오늘 재료를 지우지 않고 보관합니다.

## 막혔을 때

### 새 B 창에는 변수가 남아 있지 않음

[실습 시작 전: 두 터미널 준비](#실습-시작-전-두-터미널-준비)의 사용자·경로·그룹 이름을 B에서 다시 설정합니다. 실행이 `active`인지 읽은 뒤 명령 24~28로 실제 cgroup 경로를 다시 얻습니다. 새로 측정한다면 같은 준비 절의 `OBS` 설정과 폴더 만들기도 다시 실행합니다. CPU·메모리 프로그램이 이미 끝났는데 예전 값과 새 실행을 섞지 않습니다.

### 같은 이름이 이미 실행 중이거나 A 연결을 잃음

새 B라면 먼저 실습 시작 전의 `UNIT`을 다시 설정합니다. **호스트 B에서 지금 실습의 정확한 이름**으로 상태를 읽습니다.

#### 78. (터미널 B · 호스트 · 오류 복구 시) **기존 본편 scope의 상태와 경로 확인**

```bash
systemctl show "$UNIT" -p LoadState -p ActiveState -p ControlGroup
```

- `not-found`·`inactive`이면 남은 실행이 없으므로 실습 준비로 돌아갑니다.
- `failed`이고 `ControlGroup`이 비어 있으면 실행이 끝나고 실패 기록만 남은 상태입니다. `CG` 경로를 만들거나 A에서 종료 명령을 실행하지 않고, 아래의 `reset-failed` 명령으로 기록만 지웁니다.
- `active`이고 기존 A를 사용할 수 있으면 부하를 멈추고 명령 68~76로 정상 정리합니다.
- `active`인데 A를 사용할 수 없으면 아래 중지 절차를 사용합니다. `CG`를 아직 저장하지 않았다면 중지 전에 명령 24~28로 경로를 얻습니다.

#### 79. (터미널 B · 호스트 · A를 사용할 수 없고 본편 scope가 active일 때) **남은 본편 scope 중지**

```bash
sudo systemctl stop "$UNIT"
```

#### 80. (터미널 B · 호스트 · 본편 scope 강제 중지 후) **중지 결과와 실패 기록 확인**

```bash
systemctl show "$UNIT" -p ActiveState -p Result
```

정리가 약 5초 걸릴 수 있습니다. 강제 정리 뒤 `failed`·`Result=timeout`이 남았더라도 실행이 끝났을 수 있습니다. 더는 active가 아니고 해당 cgroup 경로도 사라진 것을 확인한 뒤 실패 기록만 지웁니다.

#### 81. (터미널 B · 호스트 · 본편 실행이 끝나고 failed 기록만 남았을 때) **본편 scope의 실패 기록 초기화**

```bash
sudo systemctl reset-failed "$UNIT"
```

unit이 이미 없다는 메시지라면 없는 상태를 확인합니다. 이름이 다른 서비스나 모든 프로세스를 함께 중지하지 않습니다.

### 180초가 먼저 끝남

`Stopped: 180-second runtime limit reached.`는 실습 프로그램 자체의 시간 제한으로 종료했다는 뜻입니다. 이 문구를 CPU 제한이나 메모리 부족의 결과로 해석하지 않습니다. A가 `/ #`로 돌아왔는지 확인하고 **B에서** 해당 상한을 복원합니다.

**CPU를 다시 측정할 때:**

#### 82. (터미널 B · 호스트 · CPU 프로그램 시간 초과 후 재측정 시) **CPU 상한을 100%로 복원**

```bash
sudo systemctl set-property --runtime "$UNIT" CPUQuota=100%
```

명령 **37부터** 새 프로그램으로 100%와 25%를 모두 다시 측정합니다. 새 PID가 나오는 것은 정상이며, 이전 실행의 처리량과 섞지 않습니다. 같은 이름의 기록 파일은 새 측정값으로 덮어씁니다.

**메모리를 다시 측정할 때:**

#### 83. (터미널 B · 호스트 · 메모리 프로그램 시간 초과 후 재측정 시) **메모리 상한을 128MiB로 복원**

```bash
sudo systemctl set-property --runtime "$UNIT" MemoryMax=128M
```

그 뒤 명령 **52부터** 새 자료와 새 현재값을 관찰합니다. CPU 실험까지 다시 할 필요는 없습니다. `Not started: input timeout.`은 Enter를 60초 동안 누르지 않아 자료를 만들기 전에 끝났다는 뜻이며, A에서 명령 53을 다시 실행하고 Enter를 누릅니다.

| 상황 | 먼저 읽을 것 |
| --- | --- |
| 준비 스크립트의 `STOP` | 화면에 적힌 파일·권한·실행 위치. 기존 rootfs는 지우지 않음 |
| A에서 `/sys/fs/cgroup`가 없음 | 그 파일은 B의 호스트에서 읽음 |
| `CG_REL`이 비어 있음 | 실제 unit의 active 상태와 A/B의 UNIT 이름 |
| CPU 결과가 예상과 다름 | 같은 PID인지, 실제 quota, 관찰 구간, 다른 실행의 영향 |
| 현재 메모리가 48MiB보다 큼 | 자료 하나가 아니라 그룹 전체 사용량임 |
| 상한 변경 전 96MiB 이상 | 변경하지 말고 부하를 멈춘 뒤 구성 확인 |

<a id="optional-oom"></a>

## 선택 부록 — 주 환경을 유지하며 별도 그룹에서 OOM 관찰

[선택 OOM 안내로](#step-24)

본편의 A는 BusyBox 셸로 남겨 두며 부하 프로그램은 종료한 상태입니다. **CPU·메모리 기본 실험의 그룹을 OOM 대상으로 사용하지 않습니다.** 새 SSH 창 **C**를 같은 VM에 열어, 짧은 관찰용 호스트 Bash와 메모리 프로그램을 별도 scope에서 실행합니다. B가 그 별도 그룹을 읽습니다.

C에서는 namespace나 chroot를 만들지 않습니다. 기존 rootfs 안에 배치해 둔 **정적 실행 파일 하나를 호스트에서 실행**합니다. 본편 A의 rootfs·PID 1 셸·cgroup은 그대로 유지합니다. 관찰용 Bash는 사건 파일이 남아 있을 기회를 주지만, 어떤 경우에도 살아남는다고 보장하지는 않습니다.

이 절은 교수자가 선택한 경우에만 진행합니다. 기본 질문은 “목표 자료가 상한보다 클 때, 어떤 기록으로 OOM과 프로세스 종료를 연결하는가?”입니다. 단지 프로그램이 사라졌다는 사실만으로 OOM이라고 판단하지 않습니다.

### 실행 위치·버전·별도 이름 확인

C에서 현재 위치를 먼저 확인합니다.

#### 84. (터미널 C · 호스트 · 선택 OOM 실험) **새 C 창의 사용자 확인**

```bash
whoami
```

#### 85. (터미널 C · 호스트 · 선택 OOM 실험) **새 C 창의 호스트 이름 확인**

```bash
hostname
```

일반 사용자와 본편 B의 호스트 이름이 나와야 합니다. C를 A의 내부 셸로 대신하지 않습니다. B에서 systemd 버전을 읽습니다.

#### 86. (터미널 B · 호스트 · 선택 OOM 실험) **systemd 버전 확인**

```bash
systemctl --version
```

첫 줄이 **253 이상**이어야 아래 scope의 `OOMPolicy=continue`를 사용할 수 있습니다. 더 낮으면 이번 선택 실행을 건너뛰고 예시로 설명합니다.

B와 C에서 **각각** 별도 이름을 저장합니다. 본편의 `UNIT`·`CG`는 바꾸지 않습니다.

#### 87. (터미널 B와 C 각각 · 호스트 · 선택 OOM 실험) **별도 OOM scope 이름 저장**

```bash
OOM_UNIT="cv4-oom-$USER.scope"
```

C에서 실행 파일의 원래 위치도 저장합니다.

#### 88. (터미널 C · 호스트 · 선택 OOM 실험) **부하 실행 파일이 있는 rootfs 경로 저장**

```bash
ROOTFS="$HOME/cloud-virtualization/assets/busybox-rootfs"
```

B에서 이전 실행이 없는지 읽습니다.

#### 89. (터미널 B · 호스트 · 선택 OOM 실험) **이전 OOM scope가 남아 있는지 확인**

```bash
systemctl show "$OOM_UNIT" -p LoadState -p ActiveState
```

`active` 또는 `failed`라면 중복 시작하지 않습니다. 아래 안내로 **이 별도 이름의 이전 실험**을 정리한 뒤 명령 84부터 확인합니다. 처음 시작하여 `not-found`·`inactive`이면 명령 93으로 이동합니다.

<summary>이전 OOM 그룹이 남아 있을 때만: B에서 정리</summary>

C는 아직 일반 사용자 호스트이므로 여기서 `exit`하지 않습니다. B에서 이름을 확인하고 별도 그룹만 중지합니다.

#### 90. (터미널 B · 호스트 · 이전 OOM scope가 남아 있을 때) **이전 OOM scope 중지**

```bash
sudo systemctl stop "$OOM_UNIT"
```

#### 91. (터미널 B · 호스트 · 이전 OOM scope 중지 후) **이전 OOM scope의 중지 결과 확인**

```bash
systemctl show "$OOM_UNIT" -p LoadState -p ActiveState -p Result
```

더는 `active`가 아닌 것을 확인합니다. `failed`가 남았다면 실패 기록만 지웁니다.

#### 92. (터미널 B · 호스트 · 이전 OOM 실행 종료 후 failed 기록이 남았을 때) **이전 OOM scope의 실패 기록 초기화**

```bash
sudo systemctl reset-failed "$OOM_UNIT"
```

이제 명령 89의 상태 확인부터 다시 진행합니다. 본편의 `UNIT` 그룹은 중지하지 않습니다.

### 작은 관찰 그룹 시작

#### 93. (터미널 C · 호스트 → 별도 scope의 관리자 Bash) **별도 OOM scope의 관리자 Bash 시작**

```bash
sudo systemd-run --scope --unit="$OOM_UNIT" \
  -p CPUQuota=100% \
  -p MemoryMax=96M \
  -p MemorySwapMax=0 \
  -p OOMPolicy=continue \
  -p TimeoutStopSec=5s \
  env ROOTFS="$ROOTFS" /bin/bash --noprofile --norc -i
```

C는 이제 **별도 scope 안의 관리자 Bash**입니다. 파일과 hostname은 여전히 호스트의 관점입니다. 본편 A의 내부 환경과 구분합니다.

`OOMPolicy=continue`는 OOM 이후 systemd가 남은 구성원을 정책상 일괄 정리하지 않게 하는 설정입니다. **커널의 OOM kill을 막지는 않습니다.** 처음 그룹을 만들 때 지정하며, 실행 도중 뒤늦게 붙이는 절차로 바꾸지 않습니다.

### 별도 그룹의 실제 경로·상한 확인

`active`, 새 그룹 경로, `OOMPolicy=continue`인지 읽습니다.

각각 `100663296`(96MiB), `0`, `0`이어야 합니다. 마지막 0은 커널의 “그룹을 함께 OOM 종료”하는 옵션을 켜지 않았다는 뜻입니다. systemd의 `OOMPolicy`와 서로 다른 층의 설정입니다.

B의 관찰 폴더도 별도로 만듭니다.

### 160MiB 요청 준비, 아직 Enter 누르지 않기

#### 103. (터미널 C · 별도 scope의 관리자 Bash · 선택 OOM 실험) **160MiB 자료 생성을 준비하고 Enter 대기**

```bash
"$ROOTFS/bin/resource-workload" memory 160
```

PID와 목표 160MiB, `Press Enter to start`가 나옵니다. **아직 Enter를 누르지 않습니다.** 프로그램은 최대 60초 동안 시작 입력을 기다리므로, 다음 B의 기록을 준비한 상태에서 시작합니다. 60초가 지나면 자료를 만들지 않고 종료하며 새 실행으로 다시 준비합니다.

### 사건의 시작값을 확보한 뒤 할당 시작

B에서 먼저 기록합니다.

#### 104. (터미널 B · 호스트 · 선택 OOM 실험) **할당 전 메모리 사건 시작값 기록**

```bash
cat "$OOM_CG/memory.events" | tee "$OOM_OBS/events-before.txt"
```

**`max`·`oom`·`oom_kill`이 모두 0인지 확인합니다.** 이미 사건 기록이 있다면 Enter를 누르지 말고 C에서 Ctrl+C로 멈춥니다. 아래 별도 그룹 정리(명령 115~119)에서 **별도 scope까지 종료한 뒤 명령 84부터** 새 그룹으로 시작합니다. 프로그램만 다시 켜면 같은 cgroup의 누적 사건은 0으로 돌아가지 않습니다. 이미 발생한 OOM을 이번 실행의 변화로 잘못 계산하지 않습니다.

현재 사용량도 기록합니다.

#### 105. (터미널 B · 호스트 · 선택 OOM 실험) **할당 전 현재 메모리 사용량 기록**

```bash
cat "$OOM_CG/memory.current" | tee "$OOM_OBS/current-before.txt"
```

이제 **C로 돌아가 Enter를 누릅니다.** 목표 자료량은 160MiB인데 전체 그룹 상한은 96MiB입니다. 할당량의 마지막 출력과 종료 여부를 관찰합니다.

### 종료 결과 읽기

`allocated_mib`의 마지막 값을 적습니다. 이는 **마지막으로 쓰기를 마치고 출력한 자료량**이며 그룹 전체의 메모리 최고값은 아닙니다.

프로그램이 끝나고 프롬프트가 돌아오면 **다른 명령보다 먼저** 종료 상태를 변수에 보관합니다. 뒤에 다른 명령을 실행하면 `$?`가 그 명령의 상태로 바뀌기 때문입니다.

#### 106. (터미널 C · 종료 직후 셸 · 실행 위치 확인 전) **다른 명령보다 먼저 종료 상태 보관**

```bash
OOM_RC=$?
```

그 뒤 실행 위치를 확인합니다.

#### 107. (터미널 C · 프로그램 종료 후의 셸 · 선택 OOM 실험) **별도 scope의 관리자 Bash가 남았는지 확인**

```bash
whoami
```

`root`이고 C의 같은 관찰 Bash에 남았다면 보관한 종료 상태를 읽습니다.

#### 108. (터미널 C · 별도 scope의 같은 관리자 Bash가 남았을 때) **보관한 프로그램 종료 상태 읽기**

```bash
echo "$OOM_RC"
```

`137`은 보통 SIGKILL 종료와 연결되지만, 숫자만으로 OOM을 확정하지 않습니다. 프로그램의 `MemoryError`와 종료 상태 2도 OOM kill을 확정하지 못합니다. C가 일반 사용자 호스트로 돌아왔다면 관찰 Bash도 끝난 것이므로, 그곳의 종료 상태를 worker 하나의 상태로 적지 않습니다.

#### 110. (터미널 B · 호스트 · 선택 OOM 실험) **종료 후 현재 메모리 사용량 기록**

#### 111. (터미널 B · 호스트 · 선택 OOM 실험) **OOM 이후 별도 scope 상태 확인**

사건의 **끝값 − 시작값**을 계산합니다. `oom_kill` 증가와 종료 결과, 실제 상한과 할당 진행을 함께 보아야 OOM kill이라고 설명할 수 있습니다. `max`만 증가했다면 같은 결론을 내리지 않습니다.
