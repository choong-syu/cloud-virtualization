## 실제로 발견하고 수정한 문제

### 1. Docker는 설치되어 있지만 Buildx가 없음

첫 점검에서 `docker buildx`를 인식하지 못했습니다. Ubuntu의 `docker-buildx`를 설치한 후 버전과 이미지 빌드가 정상 동작했습니다. 학생 문서의 시작 단계에 Buildx 확인과 설치 안내를 추가했습니다.

### 2. 기본 빌드 네트워크에서 패키지 다운로드가 멈춤

Task 2의 `RUN apk add --no-cache curl`이 완료되지 않았습니다. 점검 결과는 다음과 같습니다.

- VM 자체에서 동일한 Alpine 패키지 인덱스의 HTTPS 응답은 정상이었습니다.
- 기본 bridge 컨테이너의 DNS 조회는 성공했지만 다운로드 본문 수신이 멈추거나 시간 초과가 발생했습니다.
- 호스트 네트워크를 사용한 컨테이너에서는 같은 파일 다운로드가 완료됐습니다.
- 네 번의 A/B 비교 빌드에 모두 `--network=host`를 적용하자 설치와 캐시 비교가 정상 동작했습니다.

문서의 명령 21·22·24·25와 문제 해결 안내를 수정했습니다. 이 옵션은 빌드 중 RUN의 네트워크에 적용하며 파일시스템 격리 실습의 조건을 바꾸지 않습니다. Docker 데몬 설정 변경이나 서비스 재시작은 하지 않았습니다. 네트워크 문제의 근본 원인을 MTU 등 특정 설정으로 단정하지 않았습니다.

### 3. 학생이 복사하거나 해석하기 어려운 표현

- `printf`의 따옴표 안에 실제 줄바꿈이 있던 부분을 한 줄의 `\n` 표기로 정리했습니다.
- 긴 이미지 정리 명령을 Bash 줄 연결로 나누었습니다.
- 그림 04를 수정하여 파일 카드가 **각 컨테이너에서 보이는 내용**임을 표시했습니다. B와 새 컨테이너가 읽는 원본을 쓰기 레이어의 파일로 오해하지 않도록 출처를 구분했습니다.
- 파일 부재를 관찰하는 명령 34·36·45는 예상된 오류임을 명시했습니다.

### 캐시 비교의 핵심 로그

메시지를 Version 1에서 Version 2로 변경한 후의 결과입니다. 단계 번호와 소요 시간은 환경에 따라 달라집니다.

```text
A: COPY → RUN
#6 [2/3] COPY message.txt /app/message.txt
#6 DONE 0.0s
#7 [3/3] RUN apk add --no-cache curl
... Installing curl ...
#7 DONE 0.8s

B: RUN → COPY
#6 [2/3] RUN apk add --no-cache curl
#6 CACHED
#7 [3/3] COPY message.txt /app/message.txt
#7 DONE 0.0s
```

### 파일 격리와 수명주기의 핵심 결과

```text
파일 수정 직후 A / B / 새 실행:
Modified by Container A
Original Data
Original Data

A에서 파일 생성·삭제 후 docker diff:
C /app
A /app/new.txt
D /app/message.txt

stop/start:
컨테이너 ID 유지, Persistent Until Remove 유지

rm/run:
컨테이너 ID 변경, /app/data.txt 없음, /app/message.txt = Original Data
```

`sleep` 컨테이너는 stop 후 `Exited (137)`로 표시됐습니다. 종료 코드 0을 요구하지 않도록 안내하며, 여기서는 중지 상태·같은 ID·재시작 후 파일을 성공 기준으로 삼습니다.

## 문서·그림 검토와 한계

학생 관점의 별도 검토에서 48개 명령의 선행 조건과 관찰 지점을 확인했습니다. 각 명령의 Bash 문법 검사 48/48개를 통과했고, 문서 전체의 Bash 코드블록 49개도 문법 검사에 통과했습니다. 그림 5개의 가독성·내용 대응과 문서의 상대 링크를 확인했습니다.

그림 5장의 제목·설명·상태 표시는 한국어로 교체했습니다. 명령어·파일명·경로는 실제 표기를 유지하고, 파일 내용의 의미를 한글로 표시한 그림에는 실제 출력과의 대응을 본문에 안내했습니다. 실습 명령은 변경하지 않았습니다.

이 검증은 한 수업 VM에서 수행한 결과입니다. 다른 VM의 패키지·네트워크 상태, 향후 이미지 태그 변경까지 보장하지는 않습니다. `docker diff`와 파일 내용 비교로 변경의 독립성을 관찰했으며, 커널 내부의 실제 copy-up 순간이나 호스트 저장 경로를 직접 추적한 실험은 아닙니다.

SSH 접속 정보와 인증 정보는 공개 문서에 포함하지 않았습니다.
