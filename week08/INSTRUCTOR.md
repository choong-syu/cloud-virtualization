# 8주차 실습 — 교수자 진행 안내

[학생용 실습](README.md) · [실제 검증 기록](VALIDATION.md)

## 목표와 진행 순서

7주차의 질문은 “어떤 실행 조건으로 컨테이너를 실행하는가”였습니다. 이번에는 **실행에 필요한 파일을 어떻게 이미지로 만들고, 실행 후 변경 사항이 어디에 남는가**를 확인합니다. 학생용 문서는 명령 01~48번이며 모든 명령을 학생 VM의 일반 사용자 Bash에서 실행합니다. 터미널은 하나면 충분합니다.

| 구간 | 명령 | 권장 시간 | 수업 중 확인할 증거 |
| --- | --- | ---: | --- |
| 준비 | 01~03 | 5~10분 | Docker Client·Server, Buildx, 베이스 이미지 다운로드 |
| Task 1 | 04~13 | 15분 | CMD 설정, 메시지 출력, 정상 종료, `.dockerignore` 제외 결과 |
| rootfs 연결 | 14~15 | 10분 | 파일시스템 레이어 목록과 CMD, 컨테이너 안의 `/` |
| Task 2 | 16~26 | 20분 | 입력 변경 전후 CACHED, A/B 설치 단계의 재사용 차이 |
| Task 3 | 27~38 | 15분 | A·B·새 실행의 파일 차이, 추가·변경·삭제 목록 |
| Task 4·정리 | 39~48 | 10~15분 | ID와 파일 유지·소실, 이번 실습 자원만 삭제 |

약 75~90분을 확보하고 패키지·이미지 다운로드는 가능하면 수업 전에 마칩니다. 시간이 부족하면 명령을 생략해 뒤의 전제 상태를 깨뜨리기보다, Task 2의 순서 비교를 다음 시간으로 이어갑니다. Task 3은 자체 프로젝트를 새로 준비하므로 Task 1의 출력 파일과 혼동하지 않게 합니다.

## 교안과 실습의 연결

기준은 제공된 8주차 교안의 **실제 슬라이드 순서 1~50장**입니다. 일부 하단 페이지 번호는 이전 편집 번호이므로 아래 순서와 다를 수 있습니다.

| 교안의 실제 슬라이드 | 이론 | 대응 실습 |
| --- | --- | --- |
| 5~13, 17~18, 37~40 | Dockerfile·베이스 이미지, FROM/RUN/COPY/CMD, 빌드·실행 시점 | 명령 04~11: 이미지를 만들고 기본 CMD로 실행 |
| 14~16 | 컨텍스트, COPY 경로, `.dockerignore` | 명령 07·12~13: 마지막 `.`과 `-f` 구분, 제외 파일 확인 |
| 22~24, 35 | rootfs, 파일시스템 레이어와 실행 설정 | 명령 14~15: RootFS.Layers·Config.Cmd와 컨테이너 `/` 연결 |
| 27~30, 41~43 | 레이어 재사용, 빌드 캐시와 명령 순서 | 명령 16~26: v1/v2와 COPY→RUN / RUN→COPY 비교 |
| 25~26, 31~32, 44~46 | 이미지 원본 유지, 상위 변경·삭제, 쓰기 레이어·CoW | 명령 27~38: A/B 결과와 docker diff 비교 |
| 33~34, 47~48 | 컨테이너와 데이터의 수명주기 | 명령 39~46: stop/start와 rm/새 run 비교 |
| 36, 49~50 | 실습 종합·기록·정리 | 관찰 기록 표, 명령 47~48 |

레이어 공유와 삭제는 결과를 해석하는 이론으로 연결합니다. 이 실습이 공유 레이어의 실제 디스크 점유량, 삭제 표식 파일 또는 물리적인 copy-up을 직접 측정했다고 설명하지 않습니다. 교안 19~21장의 Nginx 웹 예제는 본문 필수 실습에 포함하지 않았습니다. 네트워크·포트 게시의 상세 실습과 Volume·Bind Mount 사용법은 다음 주차 범위를 유지합니다.

## 수업 전 준비

- 학생별 Ubuntu 24.04 VM과 sudo 사용 가능 여부를 확인합니다. root 로그인 셸에서 시작하지 않습니다.
- 7주차와 같은 Ubuntu 패키지의 `docker.io` 설치를 사용합니다. **`docker-buildx`도 확인**합니다. 준비 VM에서 Docker Engine만 설치되고 Buildx가 빠진 경우가 발견되어 학생 문서에 별도 점검·설치 안내를 넣었습니다.
- Docker 회사 저장소에서 설치한 VM에 Ubuntu의 `docker.io`·`docker-buildx`를 혼합 설치하지 않습니다. 먼저 해당 VM의 설치 방식을 확인합니다.
- Docker Hub에서 `busybox:1.36`과 `alpine:3.23`을 받을 수 있어야 합니다. Task 2의 `apk add`에는 Alpine 패키지 저장소 접근도 필요합니다.
- 버전·이미지 ID·크기·단계 번호를 정답으로 고정하지 않습니다. 같은 캐시 비교 도중 베이스 이미지를 다시 pull하거나 빌드 캐시를 지우지 않습니다.
- README를 GitHub에서 읽으며 파일 생성 블록을 복사하는 방식입니다. Git 설치, 저장소 복제, 준비 스크립트의 사전 배포는 필요 없습니다.

도구 확인은 학생 문서 명령 01의 `sudo docker version`과 `sudo docker buildx version`을 모두 통과한 뒤 진행합니다. Client만 표시되고 Server 연결이 실패한 상태에서 다음 실습으로 넘어가지 않습니다.

### 수업 VM에서 확인한 빌드 네트워크 문제

실제 수업 VM에서 기본 빌드 네트워크를 사용하는 `RUN apk add`의 다운로드가 멈췄습니다. DNS 조회는 정상이었고, 호스트의 HTTPS 요청은 HTTP 200을 반환했습니다. 반면 기본 Bridge의 BusyBox wget은 HTTP 헤더 200을 받은 뒤 본문 전송이 멈추거나 HTTPS 요청이 시간 초과했습니다. 같은 Alpine 다운로드를 host 네트워크로 실행했을 때는 바로 성공했습니다.

이에 따라 학생 문서의 **명령 21·22·24·25 네 빌드 모두 `--network=host`를 사용**합니다. 이 옵션은 빌드 중 RUN의 네트워크 접근에 적용됩니다. 컨테이너 파일시스템, 완성된 이미지의 기본 네트워크, 이후 `docker run`의 네트워크 모드를 host로 바꾸는 설정이 아닙니다.

- A/B 최초 빌드와 재빌드의 네트워크 옵션을 동일하게 유지해야 명령 순서에 따른 캐시 차이를 비교할 수 있습니다.
- 기본 빌드 네트워크가 정상인 다른 환경에서는 네 번 모두 이 옵션을 생략해도 됩니다. 비교 도중 일부 빌드에만 넣거나 빼지 않습니다.
- 다운로드가 계속 멈추면 Ctrl+C로 중단하고 옵션과 VM 네트워크 상태를 확인합니다. 실패한 설치를 캐시 비교 결과로 기록하지 않습니다.
- 대응 과정에서 Docker 데몬을 재시작하거나 기존 Bridge 설정을 변경하지 않았습니다. MTU 등 구체적인 원인은 확정하지 않았으므로 “MTU 문제를 해결했다”고 설명하지 않습니다.

이 대응의 관찰 결과와 전체 실습 재실행 결과는 [검증 기록](VALIDATION.md)에서 구분해 확인합니다.

## 설명의 경계

1. **이미지와 rootfs:** 이미지는 실행 중인 rootfs 자체가 아니라 rootfs를 구성할 파일과 변경 사항을 레이어로 제공합니다. 컨테이너 프로세스는 준비된 파일시스템을 `/`로 봅니다. `config.json`과 이미지의 CMD는 파일시스템 그 자체가 아닌 실행 조건입니다.
2. **레이어와 이력:** `RootFS.Layers`의 DiffID 목록, `Config.Cmd`, `docker history`의 제작 이력을 구분합니다. history 행 수나 Dockerfile 줄 수를 파일시스템 레이어 수로 세지 않습니다. WORKDIR 등 모든 명령의 동작을 일괄적으로 “설정만 변경한다”라고 일반화하지 않습니다.
3. **빌드와 실행:** RUN과 COPY는 이미지 제작 과정에 관여합니다. CMD의 cat은 컨테이너 시작 때 실행되고 작업을 마치면 종료합니다. 이미지 뒤의 일회성 명령이 CMD를 대체해도 원본 이미지 설정은 수정되지 않습니다.
4. **캐시:** 재사용 여부는 명령문뿐 아니라 관련 입력과 이전 결과에 의존합니다. `touch`로 수정 시각만 바꾸지 않고 파일 내용을 바꿉니다. `apk --no-cache`와 `docker build --no-cache`는 다른 옵션입니다.
5. **CoW:** A의 변경이 B와 새 컨테이너에 반영되지 않는 것을 관찰합니다. `docker diff`의 A/C/D도 변경 목록이며, 물리적 copy-up 호출을 추적한 결과는 아닙니다. 그림은 개념도입니다.
6. **삭제:** A에서 파일이 보이지 않아도 이미지의 하위 원본까지 제거되었다는 뜻은 아닙니다. 삭제 후 이미지 크기가 그만큼 줄었다고 결론 내리지 않습니다.
7. **저장 구현:** 저장 드라이버·snapshotter에 따라 내부 구현은 다릅니다. `/var/lib/docker/overlay2`를 공통 경로로 가정하거나 내부 파일을 직접 수정하지 않습니다.
8. **데이터 수명:** 모든 파일 유지 실험은 Volume·Bind Mount를 연결하지 않은 일반 쓰기 레이어를 대상으로 합니다. 컨테이너 삭제가 외부 저장 데이터까지 항상 삭제한다는 뜻은 아닙니다.

## 재실행과 자원 범위

재실행 전 기존 결과를 기록하고 `cv8-` 이름의 상태를 확인합니다. 같은 이름의 컨테이너가 남아 있으면 새 run이 실패합니다. A/B의 중간 관찰을 이어갈 때는 start/exec를 사용하고, 처음 상태로 돌아갈 때만 해당 컨테이너를 삭제 후 다시 만듭니다. Task 3에서 삭제한 message.txt를 B에서 복사해 복구시키면 원래 비교 조건이 달라집니다.

파일 작성 블록은 기존 프로젝트 파일을 덮어씁니다. 수정한 Dockerfile·메시지를 먼저 별도 보관합니다. 캐시는 지울 필요가 없으며 반복 실습의 첫 빌드도 CACHED일 수 있습니다. v1/v2 결과를 기록한 후에 새 메시지로 비교합니다.

| 종류 | 이번 실습의 생성·변경 범위 |
| --- | --- |
| 호스트 파일 | `~/week08-task1`, `~/week08-task2`, `~/week08-task3`와 그 안의 Dockerfile·메시지·제외 규칙 |
| 컨테이너 | `cv8-task1-run`, `cv8-a`, `cv8-b`, `cv8-lifecycle`, `cv8-lifecycle-new`; 이름 없는 `--rm` 컨테이너는 실행 후 자동 삭제 |
| 이미지 태그 | `cv8-task1:v1/v2`, `cv8-context:v1`, `cv8-order-a:v1/v2`, `cv8-order-b:v1/v2`, `cv8-file:v1` |
| 다운로드·캐시 | BusyBox·Alpine 베이스 이미지, 빌드 캐시, 이미지 안의 curl과 의존성 |
| 필요시 설치 | Ubuntu `docker.io`, `docker-buildx`와 의존 패키지; Docker 서비스 시작 |

정리는 컨테이너 → 직접 빌드한 이미지 태그 순서입니다. 명령 47~48은 이번 이름만 지정하며 프로젝트 원본·베이스 이미지·빌드 캐시는 남깁니다. `cv7-*` 컨테이너와 `cv7-net` 등 이전 주차 자원은 정리 대상이 아닙니다. 전역 prune을 사용하지 않습니다. 별도로 교안의 웹 예제를 실행했다면 본인이 만든 `cv8-web`도 목록에서 확인한 뒤 선택적으로 정리합니다.

## 기록과 검증

학생은 예상 출력 대신 실제 출력과 그 이유를 관찰 표에 적습니다. 핵심 채점 기준은 캐시의 명령별 변화, A/B/새 실행의 차이, 같은 ID 유지와 새 ID 생성의 구분, rootfs와 이미지의 관계입니다.

실제 실행 환경·관찰 결과·남은 제한은 [VALIDATION.md](VALIDATION.md)에 별도로 기록합니다. 이 문서의 예상 결과나 그림을 실측 검증 기록으로 대신하지 않습니다. 수업 전 해당 기록과 사용하는 VM의 Docker·Buildx 상태를 함께 확인합니다.
